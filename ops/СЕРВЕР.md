# Сервер завода: установка с нуля

Два сервера в кабинете Timeweb Cloud клиента. Основной в России, на нём всё; второй в Нидерландах, на нём только релей. Работа на полтора–два часа, из них полчаса уходит на ожидание записей домена.

Почему именно такая раскладка и страны: `docs/02-АРХИТЕКТУРА.md`, раздел 2.

**Кто что делает.** Серверы, домен и хранилище создаёт человек клиента в своём кабинете: счёт и права остаются у компании. Оператор получает вход по ключу SSH и ставит всё остальное. Токен бота Telegram в настройки релея вписывает сотрудник клиента сам.

**Правило на весь документ.** Значения ключей не вставляются в чат, в письмо и в сессию Codex. Файл окружения правится в редакторе на сервере (`nano`), а не командой с ключом в строке: строка команды остаётся в истории оболочки.

## 0. Что создать в кабинете Timeweb Cloud

| Что | Параметры | Зачем |
|---|---|---|
| Облачный сервер № 1 | регион Москва, Ubuntu 24.04, 2 ядра, 2 ГБ памяти, 30 ГБ диска; вход по ключу SSH оператора; резервные копии поставщика включены | сервер завода |
| Облачный сервер № 2 | регион Нидерланды (Амстердам), Ubuntu 24.04, самый маленький тариф; вход по ключу SSH оператора | релей |
| Хранилище S3, бакет № 1 | тип «Публичный» | ролики и картинки: площадки забирают их отсюда сами |
| Хранилище S3, бакет № 2 | тип «Приватный» | зашифрованные копии данных |
| Две записи домена | `go.ecopolisrf.ru` → адрес сервера № 1; `relay.ecopolisrf.ru` → адрес сервера № 2 | адрес завода и адрес релея |

Имена поддоменов можно взять другие: тогда они меняются в `ops/nginx/zavod.conf`, `ops/nginx/relay.conf` и `ops/relay/wrangler.toml`.

Если домен клиента недоступен дольше недели, берётся отдельный короткий домен на компанию. Завод от адреса не зависит: он записан в одной переменной `PUBLIC_BASE_URL`.

## 1. Сервер завода: система

Первый вход под `root`, дальше только под `zavod`.

```bash
ssh root@<адрес сервера 1>
```

```bash
apt-get update && apt-get -y upgrade
apt-get -y install nginx certbot python3-certbot-nginx ufw unattended-upgrades curl
timedatectl set-timezone UTC
```

Часовой пояс сервера UTC: расписание в `ops/crontab.txt` записано в UTC, московское время стоит в комментариях.

Пользователь, под которым живёт завод:

```bash
adduser --disabled-password --gecos "" zavod
mkdir -p /home/zavod/.ssh && cp /root/.ssh/authorized_keys /home/zavod/.ssh/
chown -R zavod:zavod /home/zavod/.ssh && chmod 700 /home/zavod/.ssh && chmod 600 /home/zavod/.ssh/authorized_keys
```

Ему разрешено одно действие от имени системы: перезапуск своего сервиса.

```bash
echo 'zavod ALL=(root) NOPASSWD: /usr/bin/systemctl restart ecopolis-zavod' > /etc/sudoers.d/zavod
chmod 440 /etc/sudoers.d/zavod && visudo -c
```

Сетевой экран: наружу открыты вход по SSH и веб.

```bash
ufw allow OpenSSH && ufw allow 80/tcp && ufw allow 443/tcp && ufw --force enable
```

Вход по паролю выключается (в `/etc/ssh/sshd_config`: `PasswordAuthentication no`, `PermitRootLogin prohibit-password`), затем `systemctl restart ssh`. Перед этим проверьте во втором окне, что вход под `zavod` по ключу работает.

## 2. Сервер завода: Node

В Ubuntu 24.04 из коробки стоит Node 18, заводу нужен 20 и новее. Ставится текущая долгая версия из репозитория NodeSource:

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x -o /tmp/nodesource.sh
less /tmp/nodesource.sh
bash /tmp/nodesource.sh && apt-get -y install nodejs
node -v && which node
```

Скрипт сначала скачивается и просматривается, и только потом запускается. `which node` должен ответить `/usr/bin/node`: этот путь записан в расписании и в сервисе.

Зависимостей у завода нет: `npm install` на сервере не запускается вовсе.

## 3. Сервер завода: каталоги

```bash
mkdir -p /opt/ecopolis-zavod/releases /opt/ecopolis-data /opt/ecopolis-backup /var/log/zavod
chown -R zavod:zavod /opt/ecopolis-zavod /opt/ecopolis-data /opt/ecopolis-backup /var/log/zavod
chmod 700 /opt/ecopolis-data /opt/ecopolis-backup
```

| Каталог | Что в нём | Трогает ли его выкладка |
|---|---|---|
| `/opt/ecopolis-zavod/releases/<время>-<версия>/` | код одной версии | создаёт новую папку |
| `/opt/ecopolis-zavod/current` | ссылка на рабочую версию | переключает |
| `/opt/ecopolis-data/` | очередь, журналы, заявки, файл окружения | **нет** |
| `/opt/ecopolis-backup/` | зашифрованные копии за 14 дней | нет |
| `/var/log/zavod/` | журналы задач расписания | нет |

## 4. Файл окружения

Под пользователем `zavod`:

```bash
ssh zavod@<адрес сервера 1>
```

```bash
touch /opt/ecopolis-data/.env && chmod 600 /opt/ecopolis-data/.env
nano /opt/ecopolis-data/.env
```

На первом шаге в нём три строки (имена и пояснения: `.env.example`):

```
DATA_DIR=/opt/ecopolis-data
PUBLIC_BASE_URL=https://go.ecopolisrf.ru
TG_RELAY_URL=https://relay.ecopolisrf.ru
```

Остальное дописывается по мере подключения площадок: `docs/04-ДОСТУПЫ-ПО-ПЛОЩАДКАМ.md`.

## 5. Первая выкладка

Сервис и веб-сервер ставятся до выкладки: скрипт выкладки в конце перезапускает сервис и должен его найти.

С компьютера оператора, из корня проекта:

```bash
scp ops/systemd/ecopolis-zavod.service ops/nginx/zavod.conf ops/logrotate/zavod root@<адрес сервера 1>:/tmp/
```

На сервере под `root`:

```bash
cp /tmp/ecopolis-zavod.service /etc/systemd/system/ && systemctl daemon-reload && systemctl enable ecopolis-zavod
cp /tmp/zavod /etc/logrotate.d/zavod
cp /tmp/zavod.conf /etc/nginx/sites-available/zavod.conf
ln -s /etc/nginx/sites-available/zavod.conf /etc/nginx/sites-enabled/ && rm -f /etc/nginx/sites-enabled/default
certbot --nginx -d go.ecopolisrf.ru
nginx -t && systemctl reload nginx
```

`certbot` сработает, только когда запись домена уже указывает на сервер.

Теперь выкладка. С компьютера оператора:

```bash
bash ops/deploy.sh zavod@<адрес сервера 1>
```

Вывод этой команды нельзя пускать через пайп (`| tee`, `| tail`): пайп съедает код выхода, и провал выглядит успехом.

Что должно получиться:

```bash
curl -s https://go.ecopolisrf.ru/health
```

Ответ начинается с `{"ok":true`. Дальше на сервере создаются случайные секреты завода. Команда их не показывает:

```bash
cd /opt/ecopolis-zavod/current && node src/tokens/check.mjs --init
```

## 6. Релей на втором сервере

Под `root` на сервере № 2. Система и Node ставятся так же, как в разделах 1 и 2 (без пользователя `zavod` и его каталогов).

```bash
adduser --system --group --no-create-home relay
mkdir -p /opt/zavod-relay
```

С компьютера оператора:

```bash
scp ops/relay/relay.mjs ops/relay/node-server.mjs ops/systemd/zavod-relay.service ops/nginx/relay.conf root@<адрес сервера 2>:/opt/zavod-relay/
```

Секреты релея. Файл создаётся пустым, строки вписываются редактором:

```bash
touch /etc/zavod-relay.env && chmod 600 /etc/zavod-relay.env
nano /etc/zavod-relay.env
```

```
ORIGIN_URL=https://go.ecopolisrf.ru
TG_RELAY_SECRET=
TG_WEBHOOK_SECRET=
IG_RELAY_SECRET=
```

Три секрета берутся с сервера завода: их создала команда `--init`. Переносятся они из файла в файл в двух окнах терминала, минуя чат.

Токен бота вписывает сотрудник клиента, который создавал бота у @BotFather: на созвоне с передачей управления либо со своего компьютера. Ввод на экране не виден и в историю команд не попадает:

```bash
read -rsp "Токен бота: " T && printf 'TG_BOT_TOKEN=%s\n' "$T" >> /etc/zavod-relay.env && unset T && echo " записан"
```

Честная оговорка: оператор с правами `root` на этом сервере технически может прочитать файл. Читать и копировать токен ему запрещает регламент доступов (`legal/03-РЕГЛАМЕНТ-ДОСТУПОВ.md`). Если у клиента появилось сомнение, токен перевыпускается у @BotFather за минуту командой `/revoke`: старая строка удаляется из файла в редакторе, новая вписывается тем же способом, затем `systemctl restart zavod-relay`.

```bash
cp /opt/zavod-relay/zavod-relay.service /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now zavod-relay
cp /opt/zavod-relay/relay.conf /etc/nginx/sites-available/relay.conf
ln -s /etc/nginx/sites-available/relay.conf /etc/nginx/sites-enabled/ && rm -f /etc/nginx/sites-enabled/default
certbot --nginx -d relay.ecopolisrf.ru
nginx -t && systemctl reload nginx
```

Проверка:

```bash
curl -s https://relay.ecopolisrf.ru/health
```

Ответ: `{"ok":true,"relay":"ecopolis-zavod"}`.

**Запасной релей в Cloudflare.** Код тот же, обвязка другая: `ops/relay/wrangler.toml`. Поднимается за десять минут, если второй сервер недоступен. Учётная запись Cloudflare в этом случае тоже принадлежит клиенту.

## 7. Бот, группа и адрес обновлений

Порядок важен: номера группы и людей узнаются до установки адреса обновлений.

1. Клиент создал бота и рабочую группу с темами, бот в группе администратор (`docs/04-ДОСТУПЫ-ПО-ПЛОЩАДКАМ.md`, раздел 1).
2. Утверждающий, его заместитель и ответственный за заявки написали по одному сообщению в каждой теме.
3. На сервере завода:

   ```bash
   cd /opt/ecopolis-zavod/current && node ops/set-webhook.mjs --who
   ```

   Команда печатает номер группы, номера тем и номера людей. Тексты сообщений она не показывает.
4. Номера вписываются в `/opt/ecopolis-data/.env`: `TG_GROUP_ID`, `TG_TOPIC_…`, `APPROVER_IDS`, `STAFF_IDS`, `TG_BOT_USERNAME`.
5. Адрес обновлений и меню команд:

   ```bash
   node ops/set-webhook.mjs
   ```

6. В рабочей группе команда `/help` отвечает списком команд.

## 8. Расписание

Ставится последним, когда доктор зелёный:

```bash
cd /opt/ecopolis-zavod/current && node src/doctor.mjs --live
```

```bash
crontab ops/crontab.txt
crontab -l | head -20
```

Через пять минут в `/var/log/zavod/release.log` появляется первая строка, а `https://go.ecopolisrf.ru/health` показывает время последнего прохода в поле `runnerAt`.

## 9. Резервные копии

Три слоя, каждый закрывает свою беду.

| Слой | От чего спасает | Где лежит |
|---|---|---|
| Копии сервера у поставщика (включены в кабинете) | сервер не поднимается | Timeweb, Россия |
| Зашифрованный архив каталога данных, раз в сутки | ошибочная команда, испорченный файл | сервер, `/opt/ecopolis-backup`, 14 дней |
| Тот же архив в приватном бакете | сервер потерян вместе с диском | хранилище Timeweb, Россия |

Пароль архива создаётся на сервере и не показывается:

```bash
openssl rand -base64 48 > /opt/ecopolis-data/.backup-pass && chmod 600 /opt/ecopolis-data/.backup-pass
```

Копию этого файла забирает ответственный клиента за персональные данные и хранит у себя: без пароля архив не откроет никто, включая исполнителя.

Ключи приватного бакета вписываются в файл окружения: `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_REGION`, `BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`. Это другой бакет и другие ключи, не те, что у роликов: бакет роликов открыт на чтение всему интернету.

Проверка руками:

```bash
/opt/ecopolis-zavod/current/ops/backup.sh
```

Раз в квартал архив разворачивается в пустой каталог и проверяется глазами: копия, которую ни разу не открывали, копией не считается.

## 10. Обычная работа

| Что | Команда | Где |
|---|---|---|
| Выложить новую версию кода | `bash ops/deploy.sh zavod@<адрес>` | компьютер оператора |
| Откатить версию | команда печатается в конце каждой выкладки | компьютер оператора |
| Журнал сервера | `journalctl -u ecopolis-zavod -n 100 --no-pager` | сервер, под `root` |
| Журнал задачи | `tail -50 /var/log/zavod/release.log` | сервер |
| Остановить выпуск | `/stop_release` в рабочей группе | телефон |
| Проверить всё | `node src/doctor.mjs --live` | сервер |
| Сроки ключей | `node src/tokens/check.mjs` | сервер |
| Сверить копии ключей | `npm run tokens -- --compare` | компьютер оператора |

**Выкладка не трогает данные и файл окружения.** Правка расписания (`ops/crontab.txt`) после выкладки ставится отдельно: `crontab /opt/ecopolis-zavod/current/ops/crontab.txt`.

## 11. Если сервер пропал

1. Сторож на компьютере оператора шлёт тревогу в рабочую группу в течение четверти часа.
2. Расписание на время простоя ведёт компьютер оператора: `docs/06-РАСПИСАНИЕ-И-ДУБЛЬ.md`.
3. Новый сервер поднимается по этому документу, каталог данных разворачивается из последнего архива (команда в конце `ops/backup.sh`).
4. Запись домена `go.ecopolisrf.ru` переводится на новый адрес; в настройках релея ничего не меняется, он знает сервер по имени.
5. `node src/doctor.mjs --live`, затем возврат расписания серверу: `npm run mirror -- --handback`.
