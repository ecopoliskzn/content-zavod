# Служебный приём материалов: запуск и забор редактором

Новый поток ограничен отдельной темой «Материалы» рабочей группы. Личные сообщения, заявки и история группы не опрашиваются. Подготовка и согласие на публикацию — разные действия. Текущие технические доказательства и фактическая установленная версия фиксируются отдельным протоколом, эта инструкция сама не доказывает выкладку.

## Работа существующей сессии S1/S2

Запускать из `C:/ecopolis-zavod`. Настроенный `QUEUE_API_BASE` направляет команды на российский VPS. Без него команды исполняются локально, поэтому на компьютере оператора сначала проверить штатный doctor. Не читать env-файлы и не выводить квитанции claim целиком: в них есть служебный токен, который скрипт использует сам.

```powershell
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs status
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs jobs
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs claim --id=<job-id> --owner=S1
```

`claim` сохраняет закрытую квитанцию в `data/intake-editor/<job-id>.json`; до сети сохранён requestId для безопасного повтора после перезапуска. Код не выводит токен. Повтор возвращает тот же claim, а не назначает второго владельца. В редакторский контекст переносится только разрешённое содержимое задания; токен и серверные события туда не копируются.

Редактор получает исходники через штатную закрытую медиатеку, делает публикационные производные, проверяет факты и выполняет редакторскую вычитку. Обещание сделать картинку не считается файлом. Оригинал нельзя указать как готовую публикационную версию.

```powershell
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs question --claim=<квитанция.json> --file=<вопрос.json>
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs context --claim=<квитанция.json>
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs facts --claim=<квитанция.json> --file=<проверенные-факты.json>
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs release --claim=<квитанция.json>
node C:/ecopolis-zavod/src/bot/media-intake-cli.mjs result --claim=<квитанция.json> --result=<варианты.json>
```

После изменения задания/фактов нужна актуальная версия и новый job; старый результат отклоняется. `release` возвращает текущее задание в ожидание либо помечает устаревшим. Вопросы и факты проверяются контрактом S3; подтверждать права автора или одобрять публикацию редактору эта команда не разрешает.

Формат результата: `inputHash`, `editorialReview:{result:'passed',policyVersion:<из задания>}`, `variants[]` с `channel`, `format`, `text`, `mediaIds` и `entry`. Имя entry задаётся как `mi-<materialId>-<revision>`, material как `intake:<materialId>`. Для фото-пилота entry — `post` с `image/mediaId`; text обязан совпадать с показанным вариантом, facts — с проверенным реестром задания. Транспортные поля status/approval/extra/timing/id и произвольные URL модель не задаёт. Время берётся из задания. Неподдержанный формат не объявляется готовым.

Успешный результат поступает штатными `queue add`/`submit` на обычное согласование. Сам результат не одобряет публикацию. Дальше работает прежний единственный runner. При сбое после отправки карточки сначала сверяются сохранённая фаза и фактическая очередь; неопределённый результат не вызывает слепой повтор.

## Ограничения и хранение

- Cloud Bot API: до 20 MiB на скачиваемый файл; фактический предел Telegram может быть ниже этого защитного потолка. Неизвестный размер уточняется через getFile, нулевой размер не считается успехом.
- Фото: JPEG/PNG/WebP, распознавание байтов, ffprobe и реальное ffmpeg-декодирование; до 8192 по стороне и 40 млн пикселей. Telegram photo сохраняется как полученная версия, не обязательно оригинал камеры.
- Видео: закрытый импорт MP4/MOV в пределах загрузки, до 4096 по стороне и 300 секунд, полное декодирование с ограничением времени. Поддержка импорта не означает готовность всех публикационных видеоформатов.
- Квота штатной медиатеки по конфигурации, по умолчанию 512 MiB; перед загрузкой учитываются уже занятые байты, резерв диска 1 GiB и две копии ожидаемого файла. Автоудаления нет.
- Файл, который нельзя скачать через Telegram, остаётся заблокированным. Оператор может передать его существующим закрытым SSH-путём: `node src/media/library-cli.mjs --import=<файл> --material=intake:<id> --source=<источник> --server=zavod@104.171.136.64`. Сначала проверяются квота и свободное место. Затем `node src/bot/media-intake-cli.mjs attach-original --id=<materialId> --revision=<ревизия> --file=<fileUniqueId> --media=<mediaId>` повторно проверяет хеш и декодирование закрытого оригинала именно этого материала, создаёт новую ревизию состава и запрашивает его подтверждение. Это ручная доставка, не обход проверки и не одобрение публикации.
- Целевой событийный мост A не доказан. 8 ноября официальный локальный App Server через stdio успешно выполнил initialize и thread/read существующей S3 без истории/генерации; профиль и адресация метаданных доступны. Однократную пробу `codex queue --resume` автоматическая проверка отклонила, не признав явного разрешения пользователя на межсессионную передачу. Отправки не было, обход не выполнялся. Это блокировка проверки разрешения, не доказательство отсутствия технического API. Рабочий путь B — явный забор в существующей сессии. Модельного опроса новых jobs нет, прежний сторож не выключается.
- Рабочий импорт, независимая резервная копия и публикация — три отдельных результата. Timeweb возвращал SignatureDoesNotMatch; подключение Yandex ждёт самостоятельного принятия условий владельцем. P14 не подтверждён.
