# S3: фактический контракт интеграции приёмника

Реализация 07.11.2026, v4 + rules-and-readiness-v1. Общие `src/server.mjs`, admin/runner и релей принадлежат S0; S3 их не меняет. Обычный приём не вызывает LLM, очередь публикаций модуль не изменяет.

## Точки подключения

Рабочий singleton: **`src/bot/media-intake-runtime.mjs`**. Не путать с factory `createIntake` из `src/bot/media-intake.mjs`, которая используется изолированными тестами.

- `ingest(update)` — синхронно устойчиво сохраняет разрешённое событие и возвращает `{accepted:true,event?}` или `{accepted:false}`. Вызывать после проверки webhook-secret и **до HTTP 200**. При ошибке сохранения HTTP 200 не подтверждать. `accepted=false` оставляет существующие обработчики в работе. Личные сообщения, чужая тема/роль и анонимный sender_chat не принимаются.
- `flush()` — асинхронно обрабатывает inbox, импорт и карточку. Вызывать после ACK для принятых событий, а также в существующем техническом runner для возобновления и quietMs. Новая служба/автоматизация не нужна. Собственный worker-lock не допускает двух обработчиков. Ошибка не должна ломать старые публикационные задачи.
- `handleUpdate(update)` — удобный объединённый вход для тестов; не использовать вместо разделения durable ingest и HTTP ACK.
- `admin(command,args,actor)` — только после штатной admin-аутентификации. Возвращает `{code,lines,data}`; для чужих команд `null`. Контекст actor берётся из доверенного admin-стыка, не из подписи Telegram. Никаких маршрутов принятия клиентских заявок не открывает.

Команды: `intake-configure {config}`; `intake-status {}` (алиас `intake-info`); `intake-list {}`; `intake-show {id}`; `intake-jobs {}`; `intake-claim {id,owner:S1|S2,requestId}`; `intake-result {id,owner,token,result}`; `intake-release {id,owner,token}`; `intake-question {id,owner,token,question:{text,allowOmit}}`; `intake-edit {id,revision,userId,patch}`; `intake-prepare {id,revision,userId}`; `intake-retry {id,revision,userId}`; `intake-reconcile-card {id,messageId,confirmed:true}`. `isEnabled()` — быстрый безопасный флаг для штатного pump.

Добавлена `intake-facts {id,revision,jobId,owner,token,facts:{sources[],facts[]}}`: доверенный редактор с действующим claim проверяет предоставленный источник, сохраняет цитату/локатор и относящиеся к нему утверждения. Подписи и ответы включены в input.sources как `author_statement`, но не становятся input.facts автоматически. Каждый facts item требует sourceId, буквальную claim-цитату и confirmed:true; внешний клиентский source ограничен HTTPS ecopolisrf.ru без параметров/credentials либо явно именованным документом клиента. Для слов сотрудника дополнительно требуются namedSource и sourceDate. Проверка кода подтверждает структуру/связь с цитатой, не подменяет реальную сверку редактором. Queue facts имеют штатный вид `{claim,source}`. После вопроса: ответ автора → проверка `intake-facts` текущей ревизии → release старого claim → новая подтверждённая версия задания/claim. Код не вызывает LLM на сам ответ.

Назначение координатора: допустим `coordinatorMode:'operator-admin'` с пустым coordinators[], когда оператор координирует через защищённый ADMIN API. Telegram-роль неизвестному человеку не выдаётся и автор не становится утверждающим. Команды администратора остаются за доверенным API-контекстом.

`intake-claim` возвращает текущее задание и непрозрачный claim-token для следующего result/release; это служебное владение, не ключ площадки и не разрешение публикации. Токен не показывать в группе. Production CLI S0 сохраняет requestId (32 hex) до сети; повтор того же owner/requestId восстанавливает прежний claim после потери локальной квитанции. Другой requestId/owner занятую задачу не получает. Отдельного автоматического переназначения по таймеру нет: редактор освобождает устаревший claim через release; для умершего редактора сначала подтверждается отсутствие прежнего исполнителя. Изменившийся manifest не принимается старым result. Доставка и claim при ручном режиме B фиксируются самим успешным забором задания.

## Закрытое хранение и конфигурация

Состояние — `dataPath('media-intake','state.json')`, каталог 0700, файл 0600, атомарный rename после fsync. Конфигурация согласована с S0 как отдельный `dataPath('media-intake','config.json')`: runtime читает её перед действием, configure сохраняет её туда. Содержимое, числовые ID и подписи не экспортировать в mirror; отдельный статус содержит лишь технические наблюдения и счёт. Данные заявок не читаются.

По умолчанию выключено. Нужны: `enabled`, `groupId` (только действующая TG_GROUP_ID), `topicId`, числовые `authors[]`, `coordinators[]`, `approvers[]` (только подмножество штатных APPROVER_IDS), `handoffMode:A|B`, `policyVersion`, `quietMs`, `targets[]`, `limits`.

`targets[]`: `channel`, `account_ref`, `format`, `delivery_mode:auto|manual`, `readiness:passed`, `verified_at`. Для пилота S0 подтвердил выбор **Telegram album + VK photopost**; фактические аккаунты и доказательства медиапути задаёт S0, модуль их не выдумывает. `limits`: положительные `maxFiles`, `maxBytes`, `maxPending`, `maxText`, `maxJobInput`, `maxJobOutput`, `maxCalls`. Значения задаются по измеренному пути; тестовые лимиты не являются боевыми настройками.

Импорт runtime вызывает согласованный S0 **`importTelegramFile` из `src/media/telegram-import.mjs`** с `{fileId,fileUniqueId,size,name,mime,kind,material,source,variant}`. Отсутствующий file_size передаётся как undefined: размер подтверждает download-путь, не подставляется 0. Вариант стабилен по file_unique_id, material = `intake:<id>`; возврат — закрытая original row с `{verified:true,readable:true}` после реального чтения/декодирования. Ошибки в карточку попадают только фиксированным кодом. Внешняя URL или текст исключения не печатаются. S0 расширил транспорт до фото и ограниченного видео; фактическую серверную работоспособность подтверждает его пилот. Закрытый альтернативный путь — операторский SSH/SCP импорт штатной медиатеки, не публичная ссылка на оригинал.

## Результат редактора

`result`: `inputHash`, `variants[]`, `editorialReview:{result:passed,policyVersion}`. Каждый вариант: `channel`, `format`, `text`, `mediaIds[]`, `entry` — содержимое будущей записи. Runtime использует **единый `verifyIntakeResult` S0 из `media-intake-delivery.mjs`**, а не вторую несовместимую реализацию. Проверяются schema/формат, совпадение каналов/текста/mediaId, material, детерминированное имя, штатные validate/check, **publication**-версии с parent среди оригиналов задания, чтение и SHA байтов. В фотопилоте cover/внешние URL и видеоварианты отклоняются явно; расширение формата требует отдельной проверки. Оригинал либо обещание подготовить визуал не завершает P6. Сама редакторская вычитка — действие доверенного S1/S2, модельный JSON его не заменяет.

Result не добавляет запись в очередь и не помечает её approved. Детальное имя entry обязательно `mi-${job.materialId}-${job.revision}`. Поля полномочий (`approval`, не-draft status, result, by, extra) и произвольное `entry.timing` из ответа не принимаются. Только доставка S0 строит draft и timing из доверенного задания. S0 добавляет `src/bot/media-intake-delivery.mjs` для штатного add/submit, долговечных квитанций и восстановления; общий server/runner S0 вызывает его отдельно после flush и успешного result. Наш runtime.flush не импортирует delivery, чтобы не создать цикл commands/runtime. P7–P13 до реальных квитанций очереди остаются blocked. STOP/HOLD и приём заявок не меняются.

**Разные контракты времени:** intake `after_approval` соответствует queue `after-approval`; `at`/`not_before` хранят UTC в задании, но не копируются сырым объектом в queue. `choose_later` разрешает подготовку, **запрещает submit/выпуск до явного выбора**. Delivery S0 должен проверить это до внешнего действия. `not_before` нельзя молча превращать в точный `at` с отказом при опоздании; если штатная очередь не умеет эквивалент, вариант ждёт до реализации безопасного адаптера/разрешённого изменения срока. Значение timing никогда не берётся из LLM.

## Сетевые и аварийные границы

Одна сохраняемая карточка в исходной теме. Создание сначала помечается sending; неопределённый ответ оставляет unknown и не запускает слепой второй send. После сверки конкретного messageId S0 вызывает reconcile-card; карточка обновляется edit. Передача на подготовку, архив и обсуждение не являются Одобрить.

Замок захватывается эксклюзивно. Живой/неизвестный PID никогда не снимается по возрасту; доказанно умерший PID допускает восстановление. Неизвестная отправка карточки и старый claim не объявляются завершёнными после рестарта. Права на новый файл подтверждаются для нового manifest; поздние файлы возвращают задание на видимое подтверждение новой версии, прежнее не меняется молча. Активные комплекты включают submitted/claimed; pending inbox ограничен тем же maxPending. Закрытый журнал дополнительно ограничен 16 MiB для пилота: при превышении новое событие не подтверждается, старое не удаляется. Достигнутый предел требует S0, не бесконечного роста.

Эти прогоны синтетические; P0 реального контура, реальный пилот, P9–P14 не подтверждаются ими автоматически.
