# Расписание и дубль

Кто выпускает, когда, что будет при сбое и как расписание переживает потерю сервера. Требование владельца проекта: расписание держится на сервере и дублируется на компьютере оператора.

## 1. Кто хозяин

**Расписание ведёт сервер.** Раз в пять минут он берёт одобренные записи, у которых наступил слот, и выпускает их. Компьютер оператора в обычной жизни ничего не выпускает: он держит копию, сторожит сервер и готов перехватить выпуск руками.

Причина записана опытом: в прошлом запуске расписание жило на компьютере, компьютер уснул, и за сутки не вышло пять веток. Никто не узнал об этом до вечера.

| | Сервер | Компьютер оператора |
|---|---|---|
| Очередь и журнал | хозяин | копия раз в 15 минут |
| Выпуск | да, всегда | только при перехвате |
| Согласование кнопками | да | нет: кнопки обрабатывает сервер |
| Бот, заявки, кодовые слова | да | нет никогда |
| Загрузка роликов на YouTube | нет | да: файл лежит здесь |
| Сторож | сторожит ключи, заявки, источники | сторожит сам сервер |

## 2. Сетка слотов

Слот — время по Москве, в которое запись может выйти. Источник: `zavod.config.json`.

| Площадка | Слоты (потолок) | Рабочая сетка первого месяца | В сутки не больше | Пауза между выходами |
|---|---|---|---:|---|
| Threads | 08:30, 14:30, 19:00, 20:30 | каждый день, 14:30 и 19:00 | 4 | 40 минут |
| Telegram-канал | 10:00 | будни, 10:00 | 1 | 2 часа |
| ВКонтакте | 12:00, 18:00 | пост: понедельник, среда, пятница, 12:00; ролик: 18:00 | 2 | полтора часа |
| Дзен | 11:00 | четверг, 11:00 | 1 | 4 часа |
| YouTube | 10:00, 15:00, 19:00 | вторник, четверг, суббота, 15:00 | 3 | 3 часа |
| Instagram | 18:30 | 18:30 | 2 | 3 часа |
| Rutube | 10:10, 15:10, 19:10 | 15:10 | 3 | 2 часа |
| Рассылка в боте | 11:30 | среда, 11:30 | 1 | неделя |

У площадки два списка, и это разные вещи. **Слоты** — часы, в которые площадка вообще может выпускать. **Рабочая сетка** (поле `grid`) — часы и дни, по которым запись встаёт сама. Без сетки план «две ветки в день, ролик трижды в неделю» жил только в документе: постановка брала ближайший свободный слот из всех, и четыре ветки, написанные за одну сессию, вставали на сегодня.

Сессия не выбирает время руками: команда `npm run queue -- add` ставит запись в ближайший свободный слот сетки. Посмотреть ближайшие: `npm run queue -- slots` (для ролика во ВКонтакте: `--channel=vk --kind=video`). Время руками (`--date`, `--time`) сетку обходит: так ставят срочное и тестовое, и команда скажет, если время вне слотов площадки.

**Ролик идёт следом за YouTube.** Записи одного ролика на разных площадках носят одно имя. Запись Instagram, ВКонтакте или Rutube встаёт не раньше премьеры на YouTube; если её поставили раньше либо премьеру переставили, команда называет, что переставить. То же правило стоит и на самом выпуске: пока запись YouTube с этим именем не вышла (ролик не загрузили, площадка отказала), остальные площадки ждут. Ждут не вечно: через шесть часов запись просрочится, и человеку уйдёт кнопка.

**Правила выпуска**, которые нельзя обойти:

- без «Одобрить» запись не выходит;
- запись, опоздавшая больше чем на шесть часов, не выходит: в группу уходит кнопка «В ближайший слот»;
- после простоя опоздавшие идут по одной с паузой в сорок минут, а не пачкой. Четыре ветки за пять минут площадка читает как спам;
- ночью, с 22:30 до 07:00, опоздавшее не догоняется;
- при сбое площадки три попытки с шагом в пять минут. Перед повтором идёт сверка, не вышла ли запись на самом деле: Threads и ВКонтакте сверяются через свой интерфейс, Telegram-канал по веб-витрине канала. Если сверить не удалось, запись не повторяется вслепую: в группу уходит вопрос с кнопкой. После третьей попытки тревога с кнопкой;
- ответ на комментарий слота не ждёт: уходит сотруднику в течение пяти минут после согласования;
- пакет на ручную выкладку (Дзен, Rutube без ключа, видео ВКонтакте, ответ на комментарий) публикацией не считается. Запись становится «передано на ручную выкладку», а «вышло» ей ставит сотрудник кнопкой «Выложено». В итоге дня и в утреннем плане такие записи стоят отдельной строкой, пока кнопка не нажата;
- срок выхода ролика на YouTube следует за записью. Ролик загружен закрытым с датой, и открывает его сам YouTube. Запись сняли, отозвали согласие, вернули на правку, остановили выпуск человеком: сервер снимает срок с ролика. Переставили слот: срок переезжает. О неудаче бот пишет в ответе на кнопку и в тему «Тревоги», с действием для человека;
- срок получает только ролик, на котором лежит одобренный текст. Запись правили после загрузки: на YouTube остались прежние название и описание, и после нового «Одобрить» срок не встаёт, а в слот ролик не открывается, пока оператор не выполнит `npm run yt -- --update --id=<имя>`. Бот пишет об этом в ответе на кнопку, утренний план держит такие ролики отдельной строкой.

## 4. Дубль на компьютере оператора

Три задачи планировщика Windows: `ops/windows/README.md`.

**Копия.** Раз в 15 минут задача `zavod-mirror` забирает с сервера снимок и раскладывает его в каталог `mirror/`:

| Файл | Что в нём |
|---|---|
| `mirror/РАСПИСАНИЕ.md` | расписание на две недели человеческим текстом и вышедшее за шестьдесят дней: по нему сессии смотрят, чем начинались прошлые тексты |
| `mirror/queue.json`, `ledger.json` | очередь и журнал выпусков |
| `mirror/metrics.json`, `followers.json` | цифры |
| `mirror/news.json`, `trends.json` | ящик новостей и находки |
| `mirror/funnel.json`, `questionCount.json` | воронка и вопросы из бота, только счётом |
| `mirror/comments.json` | публичные комментарии под публикациями: без автора, телефоны вычищены |
| `mirror/reports/weekly/` | недельные отчёты |
| `mirror/state.json` | когда снята копия, стоит ли выпуск |

Заявок, подписчиков и переписки в копии нет: сервер отдаёт только счёт. Текста того, что люди пишут в бот, в копии тоже нет. Это граница, которую сессии не двигают: `docs/02-АРХИТЕКТУРА.md`, раздел 5.

Эти же файлы читают сессии Codex: расписание перед написанием текста, ящик новостей, цифры для разбора.

**Сторож.** Та же задача смотрит на сервер снаружи и шлёт тревогу в рабочую группу в трёх случаях:

| Что случилось | Что придёт в группу |
|---|---|
| сервер не отвечает | «Сервер завода не отвечает. Выпуск по расписанию и бот сейчас не работают» |
| сервер отвечает, а выпуск на нём не ходит дольше 20 минут | «Одобренное не выйдет» |
| копия не обновлялась дольше полутора часов | копия на компьютере устарела |

Сервер о собственной смерти сообщить не может: это видно только снаружи. Пока компьютер оператора спит, сторож молчит тоже. Поэтому в рабочие часы компьютер не засыпает (настройки электропитания), а в `/health` сервера видно время последнего прохода выпуска: его можно открыть с телефона.

**Витрина.** Раз в сутки задача `zavod-vault` пересобирает хранилище Obsidian по свежей копии: `docs/11-ВИТРИНА-OBSIDIAN.md`.

## 5. Рубильники

| Что лежит в каталоге данных | Кто ставит | Что значит | Как снять |
|---|---|---|---|
| `STOP`, отметка человека | утверждающий командой `/stop_release`; оператор командой `npm run queue -- pause`; файл, положенный руками | выпуск стоит целиком; с роликов YouTube снят срок выхода | `/start_release` в группе либо `npm run queue -- resume`: сроки роликам возвращаются |
| `STOP`, отметка перехвата | команда `npm run mirror -- --takeover`; на самом сервере: `node src/queue/cli.mjs pause --takeover` | сервер уступил расписание компьютеру оператора. Сроки роликов YouTube не тронуты | только возврат: `npm run mirror -- --handback`. Команда `/start_release` эту отметку не снимает, кнопка «Продолжить выпуск» отвечает отказом |
| `HOLD` | сам сервер, если молчал дольше получаса и вернулся | выпуск ждёт человека: пока сервер молчал, расписание мог вести компьютер | кнопка «Продолжить выпуск» в группе; возврат расписания снимает удержание сам |
| `TAKEOVER.json`, на компьютере оператора | перехват | расписание ведёт компьютер | возврат: `npm run mirror -- --handback` |

**В файле `STOP` две отметки, и они независимы.** Выпуск стоит, пока стоит хотя бы одна.

- Утверждающий сказал «стоп» во время перехвата. Отметка ставится, компьютер оператора узнаёт о ней при ближайшей сверке и останавливается. Бот в ответе пишет, что сверка идёт раз в пять минут.
- Утверждающий сказал «старт» во время перехвата. Его отметка снята, отметка перехвата осталась: сервер молчит, компьютер продолжает.
- Возврат снимает отметку перехвата. Выпуск, остановленный человеком, он не включает и пишет об этом.

Раньше отметка была одна, с причиной. Перехват затирал остановку человека, и компьютер выпускал то, что человек остановил.

`HOLD` существует ради одного правила: **выпускает всегда кто-то один.** Сервер, который лежал два часа и поднялся, не знает, что вышло без него. Если он продолжит как ни в чём не бывало, одобренные записи выйдут второй раз. Поэтому он встаёт и спрашивает.

## 6. Перехват: сервер лежит

Делается руками и только оператором. Автоматического перехвата нет: при первом же сбое сети он дал бы двух выпускающих.

**Когда перехватывать.** Сервер молчит дольше часа, и в ближайшие часы стоят одобренные записи. Если ближайший слот завтра, проще поднять сервер.

**Перехват начинается, только когда известно, что сервер не выпускает.** Команда сначала спрашивает сервер. Исходов четыре:

| Что ответил сервер | Что делает команда |
|---|---|
| принял остановку | перехват идёт. Копия расписания снимается заново, уже после остановки |
| отказал: выпуск остановлен человеком | перехвата нет: расписание стоит по решению человека |
| отказал: не подошёл ключ оператора | перехвата нет: сервер жив и выпускает сам. Сначала вернуть доступ (`docs/04-ДОСТУПЫ-ПО-ПЛОЩАДКАМ.md`, раздел 9) |
| не ответил, в том числе ошибкой 502–504 | перехвата нет, пока оператор не остановит выпуск на сервере сам и не подтвердит это флагом `--server-stopped` |

Молчание сервера остановкой не считается. Выпуск на сервере зовёт cron. Веб-сервер упал либо оборвалась сеть между сервером и компьютером оператора, а одобренное продолжает выходить. Перехват в такую минуту дал бы двух выпускающих и задвоенные посты. Остановить выпуск на молчащем сервере можно двумя способами:

```bash
ssh zavod@<адрес сервера> "cd /opt/ecopolis-zavod/current && node src/queue/cli.mjs pause --takeover"
```

либо в панели Timeweb: сервер → «Выключить».

**Чего перехват не даёт.** Бот, формы заявок и ответы на кодовые слова на время простоя не работают: они живут только на сервере, вместе с персональными данными. Новое «Одобрить» компьютер тоже не принимает. Он выпускает только то, что было одобрено до аварии; одобренное во время перехвата выйдет после возврата, и бот пишет это в ответе на кнопку.

**Что выходит без всякого перехвата.** Ролики YouTube: они загружены заранее закрытыми с датой выхода, и YouTube открывает их сам. Обратная сторона: пока сервер лежит, «Снять» и «Отозвать согласие» для такого ролика не сработают. Если утверждающий передумал во время аварии, дату у ролика убирают руками в Студии. Сроки роликов при перехвате ведёт только сервер: компьютер оператора их не ставит и не снимает.

**Сверка с сервером.** Перехват бывает и при живом сервере: встало расписание, а бот и кнопки работают. Поэтому компьютер перед каждым проходом, раз в пять минут, спрашивает сервер и принимает от него:

- утверждающий остановил выпуск командой `/stop_release`: компьютер останавливается, после `/start_release` продолжает;
- запись сняли, отозвали согласие либо вернули на правку: на компьютере она не выйдет;
- запись исправили и одобрили заново: в копии лежит прежний текст, и с компьютера он не выйдет. Исправленный выпустит сервер после возврата;
- запись со слотом до перехвата сервер не трогал: она возвращается в расписание сама, смотреть площадку глазами не нужно;
- сервер начал запись и не закончил: она придержана до взгляда человека, вышедшие части ветки перенесены в копию;
- сервер вернулся после простоя без отметки перехвата: компьютер ставит её сразу.

Задержка до пяти минут. Запись, чей слот наступает в ту же минуту, что и «Снять», ещё может выйти: бот в ответе на кнопку так и пишет, а «Не выйдет» при перехвате не обещает.

**Чего компьютер не знает.** Это касается только молчащего сервера. Копия старше его остановки: всё, что утверждающий одобрил, снял или вернул на правку после последней копии, компьютеру не известно. Команда перехвата называет, когда снята копия и когда замечен первый отказ сервера: это и есть слепое окно. Перед перехватом оператор спрашивает утверждающего в группе, не снимал ли тот записи перед аварией.

Порядок:

1. Убедиться, что лежит сервер, а не сеть на компьютере: открыть `https://<адрес завода>/health` с телефона через мобильную сеть.
2. Перехватить:

   ```bash
   npm run mirror -- --takeover --yes
   ```

   Сервер ответил: команда остановит его, снимет свежую копию и перенесёт расписание в местный каталог данных. Сервер не ответил: команда откажет и напишет, как остановить выпуск на нём. После остановки:

   ```bash
   npm run mirror -- --takeover --yes --server-stopped
   ```

3. Разобрать записи, чей слот наступил до перехвата. Шаг нужен, только когда сервер молчит: команда печатает такие записи списком и сама их не выпустит. Между последней копией и остановкой сервер мог успеть выпустить их, а копия об этом не знает. По каждой открыть площадку глазами. Вышла:

   ```bash
   npm run queue -- mark <имя> --channel=<площадка> --link=<ссылка> --local
   ```

   Не вышла:

   ```bash
   npm run queue -- move <имя> --channel=<площадка> --next --local
   ```

   Флаг `--local` обязателен: без него команда уйдёт на сервер.
4. Включить задачу выпуска на компьютере:

   ```bash
   schtasks /Change /TN zavod-takeover /ENABLE
   ```

5. Написать в рабочую группу одной строкой: расписание временно ведёт компьютер оператора, новые согласования и бот ждут возврата.
6. Компьютер не выключать и не усыплять.
7. Сервер включают обратно, когда компьютер работает и на связи. При первой же сверке компьютер поставит серверу отметку перехвата. Сервер, простоявший дольше получаса, до этого и сам стоит на удержании. Сервер, простоявший меньше, до первой сверки выпускает сам: это до пяти минут, в которые выпускающих двое (`docs/08-РИСКИ.md`).

Во время перехвата оператор правит расписание на компьютере теми же командами с флагом `--local`: снять запись (`cancel`), остановить и включить выпуск (`pause`, `resume`). Снятое на компьютере возврат передаст серверу.

## 7. Возврат: сервер ожил

1. Сервер после простоя мог встать на удержание и прислать в группу кнопку «Продолжить выпуск». Нажимать её не нужно: пока стоит отметка перехвата, кнопка отвечает отказом, а удержание снимет сам возврат.
2. Вернуть серверу то, что сделано без него:

   ```bash
   npm run mirror -- --handback
   ```

   Команда идёт по шагам, и порядок в ней важен:

   - проверяет, что сервер отвечает. Не отвечает: ничего не трогает, выпуск на компьютере продолжается;
   - останавливает выпуск на компьютере и ждёт конца идущего прохода. Иначе запись, вышедшая в эти секунды, серверу бы не передалась и вышла второй раз;
   - передаёт серверу вышедшее со ссылками, пакеты на ручную выкладку, начатое и не законченное (ветку, у которой вышла часть реплик, сервер продолжит с места обрыва и со сверкой) и записи, снятые оператором на компьютере;
   - снимает на сервере отметку перехвата и удержание. Выпуск, остановленный человеком, остаётся остановленным, и команда пишет об этом.

   Если хотя бы одна запись не передалась, выпуск не включён ни на сервере, ни на компьютере: команду повторяют. Повтор ничего не задваивает, в журнале сервера остаётся одна строка на запись. Сервер снова лёг посреди возврата: `npm run queue -- resume --local` продолжает перехват.

   Отдельный случай: запись вышла с компьютера, а на сервере согласия на ней уже не было. Утверждающий снял её либо отозвал «да», а сервер в это время был компьютеру недоступен. Команда пометит такую строку словами «БЕЗ СОГЛАСИЯ», сервер закроет запись, чтобы она не вышла второй раз, и напишет в рабочую группу со ссылкой. Убирать ли публикацию, решает человек клиента. Случай записывается в `docs/05-ГРАБЛИ.md`.

   Второй случай того же рода помечен словами «ПРЕЖНИЙ ТЕКСТ». Пока сервер был компьютеру недоступен, запись на нём исправили и одобрили заново, а с компьютера вышел текст из копии. Публикация записана, второй раз запись не выйдет, в рабочую группу уходит сообщение со ссылкой: сравнить вышедшее с согласованным. Пакет на ручную выкладку с прежним текстом сервер заменит новым и напишет, что старый выкладывать нельзя.

   Чего возврат не передаёт: перестановку слота, сделанную на компьютере. На сервере такая запись стоит в прежнем слоте.

   Сервер поднят заново из архива: он знает меньше компьютера, архив старше копии. Вышедшее с компьютера возврат запишет в журнал сервера, даже если самой записи на нём нет. Записи, которые ждали выхода, он назовёт списком: их ставят заново и согласуют ещё раз. Подробно: `ops/СЕРВЕР.md`, раздел 11.
3. Выключить задачу на компьютере:

   ```bash
   schtasks /Change /TN zavod-takeover /DISABLE
   ```

   Забытая включённой, она ничего не выпустит: без перехвата выпуск на компьютере оператора не идёт, по копии расписания выпускать нельзя.
4. Проверить: `npm run mirror` снимает копию, в `mirror/РАСПИСАНИЕ.md` вышедшее стоит со статусом «вышло».

### Учебный перехват

Перехват и возврат проверены тестами. На живой паре машин первый раз их проходят учебно: в первую неделю, в день, когда на ближайшие часы нет одобренных записей.

1. Поставить и одобрить одну пробную запись на завтра: Telegram-канал либо ВКонтакте.
2. `npm run mirror -- --takeover --yes`. В выводе: «сервер ответил и остановлен». Команда `/plan` в группе показывает, что расписание ведёт компьютер оператора.
3. Утверждающий отправляет `/stop_release`. После этого `npm run release` на компьютере печатает «сверка с сервером: выпуск остановлен человеком». Затем `/start_release` и снова `npm run release`: «остановка человеком снята, выпуск продолжается».
4. `npm run mirror -- --handback`. В выводе: «сервер: выпуск на сервере включён». Команда `/plan` больше не пишет о перехвате.
5. Пробную запись снять.

Не сошёлся любой шаг: случай записывается в `docs/05-ГРАБЛИ.md`, и до починки правило простое. При аварии расписание не перехватывают, а поднимают сервер.

## 8. Раз в неделю

- [ ] `mirror/state.json` свежий: копия снимается.
- [ ] `npm run tokens -- --compare`: копии ключей на компьютере и на сервере совпадают. Маркеры продлевает сервер, и копия на компьютере стареет молча. Устаревшая копия обнаружится в самый плохой момент: при перехвате.
- [ ] В очереди есть одобренное на три дня вперёд.
- [ ] В теме «Тревоги» нет сообщений без ответа.
- [ ] Последняя резервная копия не старше суток: `ls -la /opt/ecopolis-backup | tail -3` на сервере.

## 9. Что бывает и что делать

| Признак | Причина | Действие |
|---|---|---|
| Запись одобрена, слот прошёл, она не вышла | потолок площадки, пауза либо догон после простоя | подождать проход; `npm run queue -- show <имя> --channel=<площадка> --history` покажет, что с ней было |
| Запись «передано на ручную выкладку» второй день | сотрудник не выложил либо выложил и не нажал кнопку | кнопка «Выложено» под пакетом в теме «Выложить руками»; ссылку можно прислать ответом на пакет |
| Бот ответил: на ролике прежние название и описание | запись правили после загрузки ролика, а на YouTube лежит прежний текст | оператор: `npm run yt -- --update --id=<имя>`. Срок встанет сам |
| Перехват отказал: «сервер не ответил» | молчание сервера не значит, что выпуск на нём стоит | остановить выпуск на сервере (SSH либо панель Timeweb), затем `npm run mirror -- --takeover --yes --server-stopped`: раздел 6 |
| Перехват отказал: «выпуск остановлен человеком» | расписание стоит по решению утверждающего | ничего не перехватывать; выпуск включает `/start_release` |
| Бот ответил: срок выхода на YouTube снять не удалось | Google не принял правку либо на сервере нет ключа YouTube | сразу: Студия YouTube → ролик → «Параметры доступа» → «Ограниченный доступ», без даты. Затем оператору: проверить ключи YouTube на сервере |
| Запись поставлена, а слот через несколько дней | рабочая сетка: площадка в эти дни не выпускает | срочное ставится флагами `--date` и `--time` |
| «Прошлая попытка оборвалась на отправке» по Telegram | сеть оборвалась после запроса, а проверить канал программа не смогла | открыть канал. Пост есть: переслать сообщение оператору, он отметит запись вышедшей. Поста нет: кнопка «Вернуть в ближайший слот» |
| В группу пришло «проверка перед выпуском не пустила» | в одобренном тексте заглушка либо предложение на площадке с ограниченным доступом | оператор правит текст и отправляет на согласование заново |
| «Не вышла с 3 попыток» | площадка отказала | прочитать причину в тревоге; после починки кнопка «Вернуть в ближайший слот» |
| Выпуск молчит, тревог нет | лежит файл `STOP` либо `HOLD` | `/plan` в группе покажет состояние |
| Компьютер оператора вышел из строя во время перехвата | вернуть серверу сделанное некому | по каждой одобренной записи с прошедшим слотом посмотреть площадку глазами; вышедшее отметить `npm run queue -- mark <имя> --channel=<площадка> --link=<ссылка>`, затем снять отметку перехвата: `npm run queue -- resume --handback` |
| Возврат отвечает «перехвата не было», а выпуск на сервере стоит | файл перехвата на компьютере потерян | то же: посмотреть площадки, отметить вышедшее, `npm run queue -- resume --handback` |
| Запись вышла дважды | два выпускающих | остановить оба (`/stop_release`), удалить дубль на площадке руками, записать случай в `docs/05-ГРАБЛИ.md` |
| Сторож молчал, а сервер лежал | компьютер оператора спал | настройки электропитания; на время отъезда оператора сторожа заменяет проверка `/health` с телефона утверждающего |
