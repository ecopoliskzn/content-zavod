# Контракт целей S3 → S2/S0, 08.11.2026

S3 меняет только intake/runtime/targets и свои тесты. Delivery/adapters — S2; server/dispatch/config/deploy — S0. Это контракт к расширению, а не утверждение боевой готовности API. Активный служебный приём темы 309 и закрытый приём клиентских заявок не переопределяются.

`target = {channel,format,delivery_mode,account_ref,readiness,verified_at}`. Поддерживаются все восемь каналов реестра; фактические пути/аккаунты задаёт и проверяет S0. `readiness:passed|not_ready`, `delivery_mode:auto|manual`; у not_ready обязательна `reason`. Наличие схемы не ставит passed. В карточке показывается ручной путь/конкретный отказ.

Форматы → queue.kind: `text|post → post` (Telegram/ВК/бот), `thread → thread` (Threads), `article → article` (Дзен); `album → post` (Telegram), `photopost|photo-post → post` (ВК), `carousel → carousel` (Instagram); `short → short` (YouTube/Rutube), `video → video` (YouTube/ВК/Rutube), `video → post` (Telegram), `reel → reel` (Instagram), `story → story` (Instagram). Для текста mediaIds=[] допустимо. Видеоформат требует видео; фотоформат требует фото. Смешанный комплект требует явного выбора для каждого target; все файлы не подставляются во все варианты автоматически. Строгое соответствие описывает `targetSpec`, ВК short не обещается.

Новый job `protocolVersion:2`, `recipient:S1|S2`, `manifestRevision`, `revision`, `inputHash`, `input.targets` и `targets` совпадают. Если есть выбранный видеоформат — один координатор S2, иначе S1. Исполнитель с иной ролью claim не получает; requestId сохраняет идемпотентность. Уже сохранённые legacy jobs без protocolVersion не теряют действующее владение. На материал одна текущая готовая версия; старый claimed освобождается явно, queued старой ревизии superseded.

**Несколько форматов одного канала поддерживаются:** стабильный `targetKey(t)=channel+':'+format`. Variant/receipts/sync/dedupe — по exact targetKey, не одному channel. `targetEntryName(job,t)` из нового `media-intake-targets.mjs`: если у канала один вариант, совместимое `mi-<materialId>-<revision>`; если больше одного, суффикс `-<6hex SHA256(targetKey)>`. Имя проверяется на <=32. Не заменять карусель сторис и не перезаписывать квитанцию по одному Instagram. S2 использует ту же функцию для canonical entry/claim результатов, S0 — exacttarget в dispatch/sync. Готовность карусели не доказывает готовности story/API.

Результат: `variants[]` — один элемент на выбранный target; `channel`, `format`, `text` (для thread/article допускается также entry.posts/title), `mediaIds[]`, `entry`. Queue.kind должен соответствовать формату; файл/cover, факты, описание и остальные содержательные поля проверяет канонический delivery S2. Общие verified facts находятся в input.facts; per-target факты — в input.targetFacts[targetKey], только явно проверенные источники, не выдуманный список модели. В variant.entry факты должны быть разрешённым соответствующим набором. input.targetMedia[targetKey] содержит выбранные исходные mediaId; результат использует только проверенные производные публикационные версии этих исходников. Исходники никогда не publication refs.

Вход: новый свободный текст допустим только от разрешённого автора в настроенной теме материалов (команды `/…` не захватываются). Цели и форматы выбираются кодом по подтверждённому составу; неподходящие варианты не передаются редактору. Кнопки «Подготовить так»/форматов/срока не являются Одобрить.

Текущее after_approval = commissioning; choose_later удерживает submit. at/not_before принимаются только как однозначное указанное время, показываются в Москве. Изменение времени не требует новой генерации содержания; после попадания в очередь срок меняет штатный queue move, собственная запись очереди запрещена.

Проверка интеграции 08.11: расширенные независимые сценарии 4/4; test:bot 143/143; vault — 0 висячих ссылок. В текущем `media-intake-sync.mjs` S0 ещё читает `job.queueResults[target.channel]`: protocolVersion=2 delivery уже пишет точные ключи. Сквозной тест `media-intake.test.mjs` (аннотация источника → result → review) проходит submit двух вариантов, но карточка не видит review. S0 требуется читать `queueResults[targetKey(target)]`, с fallback на channel только для однозначного legacy target, и возвращать format/targetKey в summary/evidence. До исправления сквозной проход не считается зелёным. Это проверка локального кода; боевого подтверждения новых форматов нет.

Обновление после интеграции S0: exacttarget sync исправлен; локальный сквозной тест аннотация → result → review снова проходит. Предыдущий абзац описывает первоначальный отказ, не текущее состояние.

## Продолжение после ответа и правки

`input.budget={maxJobInput,maxJobOutput,maxCalls}` закреплён в inputHash. Это заданные пределы сериализованного пакета и вызовов, не измеренные токены/стоимость.

S0 dispatcher читает `app.continuations()`: только claimed jobs текущей submitted версии, только после нового содержательного ответа. Возвращается безопасный envelope `{eventKey,kind:'answer',jobId,materialId,revision,recipient,answerRevision,answerHash,inputHash}` без текста ответа/автора/token. eventKey dispatcher дедуплицирует durable, как отдельную причину запуска **того же назначенного редактора**. Новый claim/job не создаётся; прежняя защищённая claim-квитанция остаётся на машине исполнителя. Ответ читается через `context(jobId,owner,token)`; там answerRevision/answerHash и текущие вопросы. Отсутствие события и повторная доставка прежнего eventKey не повод для LLM. Статус answered/conflict сам не подтверждает факт: штатная facts/resolutions сверка сохраняется.

S0 sync при фактическом queue.status=rework вызывает `app.queueFeedback(previousJobId,targetKey)`. Это внутренний code-only метод, **не admin-команда из JSON модели**. Он сам читает очередь через внедрённый runtime getQueueEntry, сверяет queue receipt id/contentHash/material/channel/status/note. Подделанные поля note/status от вызывающего не принимаются. Без доверенного reader отказ. Возвращает jobId/новую revision/noteHash; повтор того же feedbackKey возвращает то же задание. Новая/иная записка требует актуального target-владения; при активном claim переход блокируется.

Новый job scope=target-rework, parentJobId, ровно один targets[], те же закрытые исходники, права и срок, версионный inputHash. `input.rework` содержит previousJobId,targetKey,entryId,contentHash,note,noteHash,feedbackKey; note — недоверенное содержимое, не полномочия. Старый completed result/queueResults не меняется. `material.targetJobs[targetKey]` указывает активное задание каждого варианта. `app.isCurrentTarget(jobId,targetKey)` — проверка актуальности отдельного варианта. Runtime publicationBlockers использует это соответствие: изменённый target старой версии блокируется, неизменённый успешный/согласованный сосед сохраняет свой job/hash. Обычное изменение материала остаётся глобальным и требует штатной подготовки.

В `input.rework.previousResult` закреплён **только прежний затронутый вариант**: channel/format/text/mediaIds и содержательные entry.title/text/posts/facts/media(type/mediaId/coverMediaId). Нет соседних вариантов, approval, actors, claim/token или всего job. Это основа точечной правки вместе с note, не требование повторной генерации с нуля. previousResult входит в inputHash и лимит maxJobInput; переполнение возвращает input_budget до изменения revision/job/state. S0 view передаёт редактору этот отфильтрованный вариант и замечание.

S2 delivery должен проверять isCurrentTarget для каждого внешнего эффекта вместо одного material.revision===job.revision: новая редактура не переиздаёт соседние опубликованные варианты. S0 sync собирает summary из активных targetJobs, а историю ссылок хранит отдельно; rework запускать лишь из фактической очереди, не из LLM summary. Новая редакция снова проходит check/add/submit и отдельное человеческое «Одобрить». Старую rejected запись следует штатно закрыть/связать по квитанции; core не пишет очередь и не отменяет её руками. До подключения S0/S2 это локально проверенный core-контракт, а не заявленная автономность сервера.

### Fencing и квитанция принятия для S0

Core `claim(id,owner,requestId,expected)` сравнивает expected внутри той же транзакции до захвата. expected содержит materialId/revision/inputHash и, если переданы, protocolVersion/manifestRevision. Ошибка — expected_job_mismatch без изменения состояния. Дубликат того же активного requestId сравнивает immutable claim.initialInputHash, сохраняя прежний token после facts; иной expected не даёт вернуть владение.

Серверный runtime **требует все пять expected полей для intake-claim** (expected_job_required при отсутствии). S0 consumer-dispatch уже передаёт их; ручному B CLI перед забором также нужен свежий intake-jobs snapshot, затем тот же атомарный expected. Core остаётся совместимым с прямыми внутренними вызовами без expected, но серверная граница их не принимает. Это необходимо до включения автоматического supersede старых конвертов.

`intake-jobs` возвращает inputHash, claimFencingVersion=1, acceptedClaimsComplete, acceptedClaims[] и безопасный claim={owner,requestId,initialInputHash,at}, плюс answerRevision/answerHash/continuation. Без token/answer/source. acceptedClaims[] не усекается и не переписывается после facts/completed/release; элемент {requestId,owner,initialInputHash,at}. acceptedClaimsComplete=true только у созданных новой реализацией jobs; legacy история может быть неполной, флаг false. При retime queued/unknown исходный dispatch допустимо считать superseded только при queued + обоих подтверждающих флагах и отсутствии matching acceptedClaims; без них сохраняется unknown. Поздний конверт с прежним hash отклоняется сервером до захвата. Принятый ранее dispatch сверяется по initialInputHash, не изменившемуся job.inputHash.
