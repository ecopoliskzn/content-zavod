# S0 → S6: восстановление чтения VK и Instagram

05.11.2026. Выполнена безопасная диагностика на российском VPS. Наружу выведены только коды и счётчики. Повторного общего collect не было. Комментарии YouTube не запрашивались повторно: восстановление и свежий сбор выполнены отдельной S0, отчёт s0-youtube-access-restored.md рядом.

## VK: подтверждён неподходящий тип имеющегося ключа

Наличие на сервере: VK_GROUP_TOKEN=true, VK_SERVICE_TOKEN=false, VK_USER_TOKEN=false. Значения не выводились. wall.get с существующим ключом сообщества вернул HTTP 200, API error_code=27. Посты и комментарии этим запросом не получены. wall.getComments в диагностике в итоге не вызывался.

Официальная схема VK 5.199 перечисляет для wall.get и wall.getComments типы user и service, не group: https://raw.githubusercontent.com/VKCOM/vk-api-schema/master/wall/methods.json . Поэтому замена обязательного service token на имеющийся group token не является обоснованным исправлением. Свежая проверка wall.get согласуется с ограничением схемы. Выдавать или перевыпускать новый ключ автоматически не требуется и не выполнялось; нужен существующий разрешённый service/user доступ либо решение владельца о его получении. Пока этого нет, восстановление API-чтения VK заблокировано доступом. Пустой журнал публикаций завода также не покрывает прежние посты сообщества.

## Instagram: API доступен, полнота выдачи не подтверждена

Повторная metadata-проверка: feed HTTP 200, 10 media, nextPage=true. Для трёх публикаций с ненулевым comments_count запросы comments с полями только id,timestamp каждый вернули HTTP 200, data=[], следующей страницы нет. Сырые тексты и авторы диагностикой не запрашивались. me/permissions вернул HTTP 400/code100: этим ответом нельзя доказать отсутствие или наличие конкретного scope.

Причина пустой выдачи при ненулевых счётчиках не установлена. Нельзя уверенно приписать её правам, скрытым/удалённым комментариям или иной причине. Нельзя объявлять, что вопросов нет. Старый сборщик дополнительно ограничивал охват первой страницей media/комментариев и скрывал внутренние ошибки. Обе проблемы требуют отдельного учёта.

Подготовлено исправление 4e36a3b в основном репозитории, cd12248 в чистой ветке выкладки:

- Собственный адаптер src/comments/instagram.mjs проходит курсоры media, комментариев и ответов. Полные paging.next URL не используются: они могут содержать ключ. Имена используются только для исключения собственных реплик и не сохраняются.
- Не более 100 запросов на проход, пауза между запросами; повтор курсора, отсутствующий курсор, отказ и предел дают явную неполноту.
- Ненулевой счётчик при недостаточном числе видимых комментариев — явное расхождение. Новых записей при незавершённом проходе не создаётся: отсутствие новых не равно отсутствию вопросов.
- Health сохраняет агрегат coverage и при ошибке Instagram; тексты и авторы в health не включаются. Общая историческая структура health других площадок этим коммитом не переделана.

Официальный источник модели Instagram Login и прав: https://www.postman.com/meta/instagram/folder/1z5vxzu/instagram-api-with-instagram-login . Совместимость всех страниц с действующим аккаунтом ещё требует живого прохода после разрешённой выкладки.

Проверки: npm test 301/301; test:bot 143/143; doctor по-прежнему 6 отсутствующих локальных настроек и 5 юридических предупреждений, приём закрыт; vault check 561 заметка, 2293 связи, 0 висячих ссылок. Тесты сначала воспроизвели отсутствие пагинации/санитизации исключения, затем прошли. Никаких новых настроек, scope, cron, privacy, HOLD или сообщений клиенту не менялось.

Выкладка cd12248 **не выполнена**: по прямому поручению S6 оператору отправлено конкретное согласование штатного deploy с одним перезапуском и последующим collect только Instagram без --send.
